# v0.23.0 — Trust what you approve

Open a cloned repository without letting it start programs on your behalf.
Approve a command knowing you saw all of it. Hand work between local agents
without lending them the approvals you gave for your own requests.

zcoder.zsh 0.23.0 is a security-hardening release. It follows a full audit of
the code paths where a repository, a model, or another local process could run
code without your approval. Everything you already rely on keeps working:
models, profiles, workspaces, token files, saved conversations, `--yes`
launchers, and external workers. This release also collects v0.22.1 and v0.22.2.

## Built for networks you control

zcoder is made for machines you already trust: your workstation, your home
lab, the build server on your LAN, and your own Ollama host. Designing for that
setting keeps it small and quick to deploy. Remote workspaces need only a token
file, with no certificates to issue or renew, and a server you trust can work
unattended with `--yes`.

The guardrails that matter on any network are always on, and this release
makes them stronger. The README and the
[safety guide](https://github.com/ZaguanLabs/zcoder.zsh/blob/v0.23.0/docs/safety.md#deployment-model)
now describe this deployment model. The
[remote guide](https://github.com/ZaguanLabs/zcoder.zsh/blob/v0.23.0/docs/remote.md#network-security)
explains how to fence a listener with the host firewall or reach it through an
SSH tunnel or VPN.

## Project MCP servers start only after you approve them

A project's `.mcp.json` names commands to run. It can arrive with a cloned
repository, and the model can write it. Until now, opening such a workspace
started those commands. Starting with 0.23.0, project servers start only after
you approve the file's exact content:

- In the TUI, `/mcp trust` shows the file and asks for confirmation.
  `/mcp untrust` revokes the approval.
- From a shell in the workspace, `zcoder.zsh mcp trust` does the same. Pass
  `--yes` when preparing a headless server without a terminal.
- Any later change to the file, by anyone, revokes the approval until you
  review the new content. Startup, `/mcp`, `mcp list`, and headless servers
  explain what is waiting and how to approve it.

Approvals are stored under `${ZCODER_HOME}/trusted-mcp`, outside every
workspace. Your user-level `mcp.json` is unaffected and needs no approval.
Your own `mcp add`, `enable`, `disable`, and `remove` edits keep an existing
approval, but never approve servers that someone else added.

[MCP project trust](https://github.com/ZaguanLabs/zcoder.zsh/blob/v0.23.0/docs/mcp.md#project-trust)

## Patches cannot run repository commands

`apply_patch` now runs `git apply` against a private, empty repository, with
your workspace as its work tree. Git therefore never reads the workspace's own
`.git/config`. Filter drivers and other commands defined there cannot run when
a patch is applied, even if the model wrote that configuration. Your user and
system Git configuration still applies.

The file tools also refuse paths that can run code later without approval:

- Any `.git` path, in any letter case, which covers hooks and repository
  configuration.
- zcoder's own configuration directory, when it lies inside the workspace.
- Patches that create a symbolic link or retarget an existing one.

## Instructions and skills stay inside the project

A project `AGENTS.md` or project Skill that resolves outside the project, for
example through a symbolic link, is now ignored and listed by `/instructions`
or `/skills`. A repository can no longer place an arbitrary readable file, such
as a key or token, into the model's prompt. User-level guidance and Skills may
still link anywhere.

## Approvals mean what you saw

- **"Allow for session" belongs to one conversation.** `/new`, switching
  sessions, or a different remote session asks again. Restarting a server
  clears every grant. A policy you chose at startup with `--yes` is unchanged.
- **Type-ahead cannot answer the dialog.** Keys pressed in the first half
  second after an approval opens are ignored.
- **Long requests show their end first.** When a command is taller than the
  dialog, the first `y` or `a` scrolls to the end; approve after reading it.
- **Hidden characters are named.** Bidirectional overrides and zero-width
  characters, which can reorder or hide text, appear as markers such as
  `<U+202E>`. This also applies to the external-action prompt.

## Safer hand-offs between local agents

Local agents still hand work to each other automatically. Each relayed task now
comes with three protections:

- The receiver accepts work only from a live zcoder instance whose discovery
  record matches the claimed sender.
- The model is told that the sender is self-reported and that you may not have
  seen the request. It is no longer told the task came at your request.
- A conversation-wide "allow" grant covers your own requests only. Commands in
  a relayed task ask again, while a configured `--yes` policy still applies.

## A stronger sysadmin backstop

The sysadmin profile's catastrophic-command guard now also blocks deleting any
user's home directory, by absolute path or `~user`, and system program
directories such as `/bin`, `/sbin`, `/lib`, `/sys`, `/proc`, and `/mnt`.
Per-command approval remains the primary control in that profile, and none of
the paths above can bypass it any longer.

## Also included since v0.22.0

- **Faster startup (v0.22.2).** The TUI paints its first frame before loading
  MCP, instructions, skills, sessions, and the relay. In local measurements,

## Upgrade

Stop the running agent, update the checkout, and restart your usual launcher:

```sh
git pull --ff-only
git submodule sync --recursive
git submodule update --init --recursive
make compile
```

If a workspace relies on a project `.mcp.json`, approve it once after
upgrading: run `/mcp trust` in the TUI, or run `zcoder.zsh mcp trust` from that
workspace before restarting a headless server. User-level MCP servers need no
action. zcoder continues to target **Zsh 5.8 or newer**.
