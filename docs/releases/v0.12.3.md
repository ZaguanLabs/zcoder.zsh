# v0.12.3 — Bound context accounting memory

The accounting cache introduced in v0.12.2 retained full copies of history
records, including large assistant responses. Starting a new job left those
copies behind until another context inspection. Compaction could likewise
leave discarded history in the cache.

The cache now retains at most 1,024 records, with a 4 KiB limit per record and
a 1 MiB total serialized-payload budget. Larger records are accounted for
without caching their text. These bounds cover cached payload, not Zsh's array
or allocator overhead. Exact comparisons still invalidate cached values after
same-length edits. New jobs, session loads, and compaction clear the cache.

An isolated 1 MiB history fixture used approximately 3 MiB less resident memory
after accounting and reset, returning to the pre-v0.12.2 baseline. The warm
1,000-message accounting benchmark remains around 29 ms on the development
machine. Large reasoning records trade repeated parsing for bounded retention.

The investigation also compared v0.12.1 and v0.12.2 startup with matching
terminal dimensions, workspace guidance, and synthetic MCP catalogs. It did
not reproduce a several-megabyte startup increase. Core library loading differed
by roughly 50 KiB. Headless module loading remains unchanged and is covered by
the startup tests.

Compare the same memory metric when profiling: Linux RSS includes resident
shared pages; PSS apportions those pages between processes; private memory
excludes them. Terminal dimensions, MCP subprocesses, and loaded history also
affect comparisons. This release does not promise a universal 2.8 MiB footprint.

The regression tests cover record and aggregate bounds, multibyte text,
same-length edits, oversized reasoning, history shrink, compaction, and reset.
No new runtime dependency or session-format change is introduced. Restart a
running instance to use the fix.
