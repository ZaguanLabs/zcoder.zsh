# v0.22.0 — Background commands, visible tools

Start a long test suite and keep the conversation moving. Change your project
instructions and have the next API turn pick them up. Know when an MCP server
is missing instead of wondering why the agent never uses it.

zcoder.zsh 0.22.0 brings background commands to the local terminal interface,
better context discovery for Ollama cloud models, and clearer behavior for
headless agents. This release collects the changes since **v0.21.0**, including
the fixes shipped in v0.21.1 through v0.21.5.

## Let long commands run while you work

In the local TUI, the model can now start an approved command with
`background: true`. The tool returns a task ID immediately, leaving you free
to continue the conversation while a build or test suite runs.

- The footer shows running tasks and results waiting for follow-up.
- `/tasks` lists tasks; `/tasks cancel task-1` cancels one and retains its
  available output.
- Completion is delivered once, in the conversation that started the command.
  If you switch conversations, the result waits until you return.
- The agent follows up after the foreground turn and queued user follow-ups
  finish. It makes no model requests just to poll for progress.

Background commands retain the normal workspace, safety, and command-approval
checks. They default to a 24-hour timeout and support up to 32 running or
undelivered tasks. Output uses the existing bounded head/tail reader.

Tasks belong to the running zcoder process. Quitting cancels them; workers
also watch for parent loss and terminate their process groups after a crash.
Tasks are not restored after a restart, and completed side effects cannot be
rolled back. This first implementation is **local-TUI only**: remote clients,
headless servers, ACP, and one-shot runs do not advertise background execution.

[Background command guide](https://github.com/ZaguanLabs/zcoder.zsh/blob/v0.22.0/docs/background-tasks.md)

## Give cloud models the right context budget

Automatic context sizing now distinguishes a local model's loaded allocation
from a cloud model's reported context limit. zcoder reads cloud metadata from
Ollama's `/api/show`, including aliases identified through their remote metadata.
Headless readiness checks can recognize a cloud model without requiring it to
appear in the local running-model list.

When cloud metadata does not report a limit, internal accounting uses a
**262,144-token fallback**, configurable with `ZCODER_CLOUD_CONTEXT_FALLBACK`.
In automatic mode, cloud requests omit `num_ctx`, leaving context selection
to Ollama. Explicit context-window settings remain supported.

Local models retain allocation-based accounting and the conservative initial
fallback for unloaded models. The context inspector and compaction threshold
use the discovered budget.

## Keep API guidance current, and show missing capabilities

Long-running API listeners no longer leave each new turn with their startup
snapshot of project guidance. API workers reload the `AGENTS.md` instruction
chain and MCP configuration before each turn, including changes and removals.

Unavailable MCP servers now produce a conversation warning and an explanatory
section in the model's system prompt. Healthy servers remain usable, and the
failure information is present even when no MCP tools connect. Identical
failures are reported once during an API turn rather than repeated for every
model request.

Missing executable diagnostics name the command and explain how to correct
the service `PATH` or configure an absolute executable path. For headless
deployments, remember that a login shell and a service can have different
environments; include the MCP executable's installation directory in the
service environment. MCP transport remains **stdio-based** in this release.

These changes improve what the model is told and make connection problems
visible. They do not guarantee that every model will follow every instruction.

## Start fresh remote conversations reliably

Empty drafts are deliberately absent from saved-session listings. Remote
clients now retain a newly created or explicitly selected empty conversation
when it is absent from that list, instead of treating the omission as evidence
that the server selected a different session. A conflicting listed selection
still triggers the existing synchronization safeguards.

This release also adds a detailed session-browsing API specification, refactors
turn and command handling into smaller helpers, strengthens HTTP response and
JSON recovery coverage, and fixes `--help` to show the default Ollama host
without replacing an environment-configured host.

## Upgrade

Stop the running agent, update the checkout, and restart your usual launcher:

```sh
git pull --ff-only
git submodule sync --recursive
git submodule update --init --recursive
make compile
```

Existing models, profiles, workspaces, token files, and saved conversations can
be retained. Finish or cancel any background commands before restarting.
zcoder continues to target **Zsh 5.8 or newer**.
